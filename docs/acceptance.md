# Приёмка на настоящем VPS

Этот список — процедура проверки, **не отчёт о пройденных тестах**.
Заполнить результаты, дату, версии клиентов и конфигурацию VPS после испытания.
На момент подготовки проекта production DNS, TLS, контейнеры и звонки
на VPS не проверены. API smoke/CI не доказывает передачу медиа.

## Базовая инфраструктура

- [ ] Три A-записи cateam.online ведут на текущий публичный IPv4; лишних AAAA нет.
- [ ] `make config` завершается успешно; Compose не содержит build/privileged.
- [ ] `make deploy` завершается, все постоянные сервисы running/healthy.
- [ ] HTTPS открывается без TLS warnings на всех трёх доменах.
- [ ] `make smoke` проходит, публичный admin API возвращает 404.
- [ ] При закрытой федерации запрос federation version получает 403.
- [ ] PostgreSQL 5432, Synapse 8008, LiveKit 7880 и auth 8080 недоступны снаружи.
- [ ] `make admin` и `make user` создают аккаунты; публичная регистрация запрещена.
- [ ] Вход в Element Web, Desktop и Android/iOS Element X проверен отдельно.

## Переписка и сохранность

- [ ] Два пользователя создают приватную комнату и видят сообщения друг друга.
- [ ] Группа 6–10 пользователей может общаться в общей приватной комнате.
- [ ] Изображение и файл загружаются и скачиваются другим участником.
- [ ] Файл более MAX_UPLOAD_MB отклоняется; новый маленький файл принимается.
- [ ] E2EE-комната работает; устройства верифицированы, recovery key сохранён.
- [ ] После `make restart` старые сообщения и вложения доступны.
- [ ] `make rtc-check` выдаёт корректный JWT, проходит SFU WebSocket upgrade.
- [ ] Пользователь вне комнаты не получает LiveKit токен (в CI отдельный сценарий).

## Реальные звонки

Подготовить **шесть отдельных участников/клиентов**, минимум один Android,
два подключения из разных домашних сетей и одно через мобильного оператора.
Сохранить версии приложений и браузеров. Нельзя заменить этот тест шестью
вкладками одного компьютера: они не проверяют разные NAT/устройства.

1. Начать голосовой MatrixRTC-звонок в приватной комнате. Проверить двусторонний
   звук, mute/unmute, смену устройства и выход/повторный вход.
2. Подключить шесть участников с видео. Начать с 360p/720p. Убедиться, что каждый
   видит и слышит других; выполнить 30–60-минутный звонок.
3. Показать экран из Element Web/Desktop, переключить окно/вкладку, закончить
   демонстрацию. Остальные участники должны получать изображение и слышать звук
   в пределах возможностей ОС/браузера. Screen sharing на телефоне проверить
   только если его поддерживает выбранный клиент.
4. Проверить индикатор шифрования и доверенные устройства. Не считать обычный
   TLS transport доказательством E2EE медиа.
5. Отключить UDP на **клиентской тестовой сети**, не на VPS. Проверить fallback
   ICE/TCP или TURN/TLS. Отдельно проверить relay candidate, иначе успешный звонок
   не доказывает, что TURN используется.
6. Для принудительной проверки TURN применить тестовый клиент LiveKit/браузера
   с relay-only ICE policy либо блокировать прямые SFU медиапорты на клиенте,
   сохранив доступ к 3478/5349. Не менять общую production политику доступа.
7. Смотреть `chrome://webrtc-internals`, Firefox `about:webrtc` или диагностику
   клиента: выбранная ICE pair, candidate type relay, протокол, потери, RTT,
   bitrate и frame drops. Секреты/JWT в экспортируемых дампах удалить перед передачей.
8. Прервать сеть одного участника, дождаться исчезновения/восстановления участия.
   Звонок не должен оставаться зависшим после выхода всех пользователей.

Результаты:

| Сценарий | Результат / дата / версии / замечания |
|---|---|
| Голосовой звонок | Ещё не выполнен |
| Видео 6 участников | Ещё не выполнен |
| Screen sharing | Ещё не выполнен |
| Android из мобильной сети | Ещё не выполнен |
| TURN relay из другой сети | Ещё не выполнен |
| TURN/TLS с заблокированным UDP | Ещё не выполнен |
| Шифрование между устройствами | Ещё не выполнено |

В сетях с доступом только TCP 443 текущий TURN/TLS 5349 может быть заблокирован.
Такой отрицательный результат нельзя выдавать за исправный relay; потребуется
дополнительная L4/SNI-схема или отдельный IP.

## Нагрузка и диск

- [ ] Во время 6-стороннего звонка периодически записывать `make doctor` и `docker stats`.
- [ ] Нет OOMKilled, неожиданных рестартов, устойчивой CPU saturation и нарастающих потерь.
- [ ] Проверить реальную пропускную способность VPS и лимит трафика провайдера.
- [ ] При неприемлемой нагрузке снизить качество/частоту экрана, затем повторить тест.
- [ ] Таймер monitor активен. Проверить guard **без заполнения диска**: временно
      поднять MIN_FREE_DISK_GB выше доступного, выполнить `make monitor`, убедиться
      в HTTP 507 для маленького upload, вернуть значение и повторить monitor.
- [ ] Таймер TLS активен, `make renew` успешно завершается, журнал проверен.

## Восстановление

- [ ] Скопировать полную backup-копию вне VPS; проверить COMPLETE/SHA256SUMS.
- [ ] В изолированной новой установке с пустыми volumes выполнить `make restore`.
- [ ] Проверить прежний server_name/signing key, вход, старое сообщение и вложение.
- [ ] Подключить клиент с сохранённым recovery key и проверить расшифровку истории.
- [ ] Не запускать старую и восстановленную установки одновременно с одним Matrix server_name.

Проект принимается после фактического выполнения нужных сценариев. Фиксировать
отрицательные результаты и ограничения; число пользователей само по себе
не гарантирует производительность видеозвонков.
